# 世界系统路线图（M1 + M2 已实现）

> 分仓：`E:\miner\wt\d2`（git worktree，分支 `d2`）。
> 本文档记录"世界机制"（局部冲突状态机 → 供需 → 货舰行为）的整体设计讨论结论、
> 已拍板的参数、M1 的具体实现，以及后续里程碑的范围划分。后续每次拍板新内容，

## 0. 背景与目标

现有经济系统（`Economy.gd`/`Freighter.gd`/`GameData.gd`）已经有一套"限价挂单 + 货舰自动撮合"
的本地市场，但"战争"只是一个全局二值开关（`war_active()`，确定性周期 8 天和平 + 4 天战时，
军用货物需求 ×1.6）。本项工作把这个占位开关换成一个更有叙事感、且与玩家交易行为联动的
"世界机制"：真实世界的大型战役（如沙漠风暴）在开打前有数月级的物资调度/囤积，战争本身反而
打得很快；星际战争烈度更高，但为了可玩性压缩了时间线。

设计讨论的完整过程见本文档"附录：讨论纪要"，这里只记录**结论**。

## 1. 总体框架（分层）

```
实体层：阵营（2 大国 + 10 小国 + 20 托拉斯 + 1 片海盗开拓地）
   ↓
阵营归属层：国家 → 阵营(Bloc)；企业默认中立
   ↓
版图层（星图落地前用占位三档效率代替真实跳数图）
   ↓
世界心跳：局部冲突状态机（筹备→开战→和平，循环）
   ↓
经济桥接层：两个输出
   ① 货舰来访频率乘数
   ② "发牌员"（采购代理）阶梯买单——订单墙
   ↓
表现层：现有 post_event 事件流（先用）；未来战略地图（M3+）
```

补给效率是**唯一一个函数** `supply_efficiency(faction)`，三处复用：版图攻防结算（M3+）、
玩家反哺折算（M1 已用）、货舰扫货积极性（M1 的"烈度"已间接体现，M2+ 可直接接入）。
星图落地前用三档占位（核心/边境/开拓地），接口不变，以后只换内部实现。

## 2. 已拍板的关键决策

| # | 问题 | 决策 |
|---|---|---|
| 1 | 玩家反哺权重 | 物资积累"100 分"里玩家只吃得到其中一小份——不是人工设硬上限，而是让"发牌员"的需求基数远超单站产能，天然形成这个效果；上限先不做，测试后再看感受调整 |
| 2 | 订单墙的视觉呈现 | 不是一条巨量买单，而是**同一货物挂好几档买单**（价格微调、分开几条），在订单簿上堆出"量大"的直觉；M1 先做"价格都在当前价附近小幅抖动"的低成本版，不做真实深度曲线（阶梯价格从低到高/走量到加急）——后续按实测手感再决定要不要细化 |
| 3 | 核心星区/补给效率的具体拓扑 | 星图没做之前无法拍板，先用**可替换的占位接口** `supply_efficiency()`：三档常量（核心/边境/开拓地），等真实星图落地后只替换内部实现 |
| 4 | 多站点扩张 | 认可"以后可扩张，地图随之变化"，但明确指出这需要自动化生产/挂单系统打底，否则多站点玩不转——**M1-M3 阶段冻结多站点与自动化，只做单站点**；自动化系统作为独立于世界机制的模块，排在 M4 单独设计 |
| 5 | 多战线支持 | 认可长期可以支持多条战线同时开打，但**M1 阶段减少战线数量**：只做"帝国 vs 南方联盟"一条主线，10 个小国的外交/战争先冻结（数据骨架保留，逻辑不接入） |
| 6 | 玩家反哺上限 | 不设限，先上线测试，根据实际手感再决定要不要加软上限 |
| 7 | 冲突规模与节奏 | **局部冲突**（不是倾国之战）：1 个月筹备 + 10 天开战 + 2 个月和平，循环往复 |
| 8 | 发牌员是否占泊位 | **占用正常泊位**——因为发牌员就是"以货舰的形式"在挂买单，这样机库等级在战时会有新的战略意义（机库建得好才接得住战争财） |

## 3. M1 范围（本次实现）

- **只有一条主线**在跑状态机：帝国 vs 南方联盟的局部冲突；10 小国、20 托拉斯只有数据骨架
  （`GameData.WORLD_FACTIONS`），不接入外交/战争逻辑。
- **节奏**：`GameData.WORLD` 配置 `peace_days=60 / buildup_days=30 / war_days=10`，纯按
  `Economy.day` 推导相位（和 `Economy.war_active()` 的周期写法同一个思路，不占额外存档字段）。
  > 换算成真实时间：`ECON.day_length=240` 秒/天 → 一整条"和平+筹备+开战"循环 = 100 天 ≈
  > 6.7 小时连续游玩。这个数字目前是**沿用现有 day_length 直接套用天数**算出来的，如果实测
  > 觉得节奏偏慢/偏快，建议和 `ECON.day_length` 一起调（见"后续调参建议"）。
- **物资积累 stockpile**：筹备期每天累积"背景经济"份额（`background_fill_ratio=0.7`，即
  玩家什么都不做，到筹备期结束也能到目标值的 70%）+ 玩家实际卖出军需品的反哺（按**货值 ×
  补给效率 × player_contrib_scale** 累加，不设上限）。开战期**不再接受玩家反哺**，只按固定
  节奏消耗（`war_initial_stockpile / war_days` 每天线性燃烧），对应"战争节奏先走固定时长"
  的拍板——这个简化是为了让 M1 尽快能跑起来，后续如果想让"打得够猛可以提前结束"也不难加。
- **输出①：货舰来访频率乘数** `WorldState.freighter_frequency_mult()`：
  和平 1.0；筹备期从 1.1 线性爬升到 1.6（越接近开战日调度越密）；开战期固定 2.0。
  接入点：`Economy._roll_visit_schedule()` 里原来写死的 `mult := 1.0`。
- **输出②："发牌员"订单墙**：筹备/开战期间常驻一艘特殊货舰（`Freighter.is_dealer=true`），
  对 `GameData.MILITARY` 里的每种军需品同时挂 `dealer_tiers=3` 档买单，价格在
  `Economy.suggest_price()` 参考价附近 ±6% 抖动（低成本版）；数量基数远超单站产能
  （`dealer_qty_base`，舰船类单独用小基数 `dealer_ship_qty_base` 避免离谱的"单站造出两千艘
  战舰"）；占用正常泊位（`Economy.dock_special_freighter()`），停留时长跟着"本相位剩余天数"
  走（`Freighter.dwell_override`，每天刷新一次续命 + 重新生成报价），不吃"货单吃满就走"的
  规则（`Economy._auto_trade()` 对 `is_dealer` 特判跳过）。

## 3.5 M2：10 小国解冻（已实现，2026-10-02）

### 拍板的关键决策

| # | 问题 | 决策 |
|---|---|---|
| 1 | 倒戈事件要不要接数值 | **轻微接入供需**：不只是文字播报，`supply_efficiency()`（玩家反哺折算）和 `_demand_scale()`（发牌员扫货规模）都会按"当面主战方的小国盟友数"做 ±系数修正 |
| 2 | 10 小国初始阵营归属 | **5 帝国 + 5 南方联盟**对半分配 |
| 3 | 倒戈触发节奏 | 挂在主线节奏上：**每次 PEACE→BUILDUP 触发一轮**，10 国各自独立判定，不单开计时器 |
| 4 | 倒戈后归属要不要持久化 | **要**，写进 `world_state_save.json` 的 `minor_bloc` 字段，跟 `stockpile` 一起存 |
| 5 | 10 国正式名字 | 团队已有命名计划，这次先用占位名 `国1`~`国10`（`GameData.MINOR_FACTIONS` 的 `name` 字段），以后原地替换即可，不影响 key/存档结构 |

### 实现要点

- `GameData.MINOR_FACTIONS`：10 条占位数据骨架，`bloc` 字段是初始值（5:5），运行时真实归属在
  `WorldState._minor_bloc`（随档持久化，不读这张常量表）。
- `GameData.WORLD` 新增 `minor_defect_chance`(0.12) / `minor_ally_mult_per_nation`(0.03) /
  `minor_ally_mult_min`(0.7) / `minor_ally_mult_max`(1.3)。
- `WorldState._roll_minor_defections()`：筹备期开局时对 10 国各自掷一次骰，命中则翻转 bloc 并
  逐条 `post_event` 播报（"边境风声：国X 倒戈——阵营由【A】转投【B】"）。
- `WorldState.ally_count(bloc)` / `_ally_mult(bloc)`：盟友系数 = `1.0 + (ally_count-5) × 0.03`，
  夹在 `[0.7, 1.3]`（当前 ±5 国的摆动上限是 ±15%，正常碰不到夹限，留作以后调参/国家数变化的安全网）。
- 接入点：`supply_efficiency(faction_id)` 和 `_demand_scale()` 各乘一次 `_ally_mult(...)`——
  5:5 基线下乘数=1.0，对 M1 已有行为零影响（回归安全）。
- **这次没有新开战线**：10 小国只是"挂靠在 empire/southern 某一方下的静态标签 + 可倒戈"，不会
  自己触发筹备/开战的独立状态机——多战线仍然是 M3 的范围，没有提前做。
- 新增测试段 `_test_minor_defection()`：验证初始 5:5、20 轮筹备期后至少触发过一次倒戈（统计性
  断言）、阵营总数守恒=10、人为极端分布下盟友系数与补给效率的单调性。

## 3.6 与星图/领土/UI 的接口边界（2026-10-02 审查记录，供后续对接）

### 跟星图/领土完全解耦——没有提前做的部分

审查过全项目，确认**没有任何星图/星系图/Sector/Territory/多站点管理的代码、场景或资源**，
哪怕是占位壳都没有。当前 WorldState 的状态机只知道"现在是筹备/开战/和平""物资积累多少"，
**完全不知道、也不影响任何空间/领土状态**——没有"帝国占了哪个星域""前线推到哪"这类概念，
因为根本没有能承载这些概念的数据结构。`supply_efficiency(faction_id)` 虽然签名已经带
`faction_id` 参数（为真实星图预留），但内部只读一个全局常量 `STATION_REGION`，不做任何拓扑
计算。这跟路线图 M3（真实星图）/M4（多站点）的冻结范围严丝合缝，不存在越界实现或遗漏连线。

### 给新闻播报 UI 的对接点

- **主要数据源**：`Economy.event_posted(text: String, kind: String)`——所有叙事文本（相位切换、
  发牌员到港/撤离、10 国倒戈）都走这一条全局信号，跟现有事件日志 UI 共用管道，直接订阅即可
  拿到完整文本流，不需要额外接 WorldState。`kind` 取值 `info`/`good`/`rare`/`warn`，世界系统
  消息多为 `warn`（筹备/开战/倒戈）和 `info`（和平/平息）。
- **结构化数据**（如果要做常驻角标，而不是纯文本滚动）：
  - `WorldState.phase_changed(phase_name: String)` —— 相位切换时触发一次
  - `WorldState.stockpile_changed(value: float, target: float)` —— 物资积累变化时触发
  - `WorldState.dealer`（`Freighter` 或 `null`）—— 判断发牌员在不在港
  - `WorldState.ally_count("empire"/"southern")` —— 查某一方当前小国盟友数
- **已转正**（UI 线并行会话完成，2026-10-03~04）：`current_faction`、`phase_name(p:=-1)`、
  `phase_progress(day:=-1)`、`days_left_in_phase(day:=-1)` 已去掉下划线转为公开接口，外加新增
  `faction_display_name()`；`scripts/ui/NewsTicker.gd` 已基于这几个接口开始实现新闻播报条。

## 3.7 审查 MissionOps（探索派遣系统）对 M2 的影响（2026-10-04）

审查了 `docs/MissionOps系统报告.md` + `docs/探索派遣系统蓝图.md`（§1 边界声明/§5.10 海盗联动/
§15 装备体系/§17 拍板点）。结论：**架构上对 WorldState 是真零依赖**（蓝图 §1 白纸黑字："不读
冲突相位、不读阵营、不读 `supply_efficiency()`"），M1-M3 阶段不会调用任何 M2 新增接口。但有
几个"纸面零依赖、运行时仍会碰到一起"的点记录如下，供双方以后排查问题时参考：

1. **舰船商品池共享**：MissionOps"启用"机制从 `Economy.inv` 里抽一艘已建造的船转成锁定编队
   实例；而 `longbow/raven/ram/logistics` 这 4 个船型 id 正是 `GameData.MILITARY` 成员，也正是
   M2 发牌员筹备/开战期会高价扫货的对象。两边抢同一批库存——玩家会面临"卖给发牌员换钱"还是
   "启用编入探索舰队"的真实取舍。良性涌现互动，不是 bug，但战时发牌员扫货可能让玩家一时凑不出
   船去出征，值得双方心里有数。
2. **`GameData.MILITARY` 命名空间提醒**：MissionOps 的四槽子系统装备（能源/电子/武器/防御）会
   往 `LICENSE_CATALOG` 加新行，但**不应该**把这些新装备 id 顺手塞进 `GameData.MILITARY`——否则
   会被发牌员订单墙覆盖、拉高战时需求倍率、被当成军需品扫货，这大概率不是 MissionOps 想要的
   效果（它们是探索系统专属掉落/制造物）。目前没有发生，只是实现期容易踩的坑，提前打个预防针。
3. **存档形态未来可能合流**：MissionOps §6.3 计划建一个全新的 `GameSave`（节注册制）公共存档器
   自己先接入；WorldState 目前是独立手写 `world_state_save.json`（故意不碰 Economy 存档结构）。
   `GameSave` 真落地成为项目标准后，WorldState 这个小独立档要不要迁移进去统一管理，是迟早要议
   的点，现在不急，先记一笔。
4. **"M2" 撞名提醒**：MissionOps 自己也有"M2 完整循环"里程碑（报告 §8），跟世界系统"M2：10
   小国解冻"是两条完全独立的进度线，纯属巧合撞了名字——蓝图 §5.10"阶段1随 M2 实装"指的是
   **MissionOps 自己的 M2**，没有功能关联。以后对话/审查时注意别认错。

## 5. 后续调参建议（不是本次要做的，先记下来）

- 如果实测觉得"6.7 小时一个完整周期"太长，有两个独立的调节旋钮：改 `GameData.ECON.day_length`
  （影响全局，包括货舰停留、建造工期等）或只改 `GameData.WORLD` 的天数配比（只影响这条战争线）。
  建议先改后者，影响面小。
- `dealer_price_jitter`（±6%）和"阶梯都在当前价附近抖动"是刻意选择的低成本方案；如果后续想要
  "大宗走量便宜、小单加急贵"的真实深度曲线，只需要改 `WorldState._refresh_dealer_offers()`
  一个函数，不影响其他地方。
- `player_contrib_scale`（0.00006）是没有任何实测数据下的占位猜测值，强烈建议上线后先观察
  "卖一批军需品，stockpile 大概涨多少"的实际数字，再反推调整。

1. **起点**：审查交易/市场系统时发现这是一套 EVE 式限价挂单经济（而非最初误判的旧版 2D
   GameMaker 原型），`war_active()` 只是一个占位性质的全局二值开关。
2. **诉求**：设计一个"世界机制"框架，用供需关系驱动货舰的挂单与扫货意愿，背景设定为
   帝国 / 南方联盟两大国 + 10 小国 + 20 托拉斯 + 1 片海盗开拓地，未来还要有战略地图。
3. **分层框架讨论**：提出"阵营归属"代替 N×N 关系矩阵、"实力对比驱动概率漂移"代替逐格
   战棋模拟、海盗作为独立的风险系数而非参与阵营对抗的第四方。
4. **沙漠风暴类比**：战前物资调度 → 玩家反哺是"其中一份"而非全部 → 补给效率随距离己方
   核心衰减（同一条规则同时解释"攻难守易"）→ 海盗劫掠专打远途航线。
5. **收敛为可执行的两个输出**：货舰来访频率、货舰扫货积极性 + 离港前挂买单。
6. **拍板环节**（见第 2 节表格）：把"离港前挂买单"具体为"发牌员以货舰身份常驻挂阶梯买单"；
   星图没做之前用占位补给效率；M1 冻结多站点/自动化与多战线；局部冲突节奏定为
   1 个月筹备 + 10 天开战 + 2 个月和平。
7. **M1 启动**：在 `E:\miner\wt\d2` 分仓实现，详见第 3 节。
